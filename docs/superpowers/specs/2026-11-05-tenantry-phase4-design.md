# Tenantry — Phase 4 design: Customer applications

Date: 2026-11-05 · Status: draft for review

## Purpose

Phase 4 lets an enterprise workspace plug its own apps into its realm. An owner or admin registers an app in the portal; our API creates the Keycloak client in that tenant's realm, shows the connection details (a secret only once), and lets them test the sign-in, rotate the secret, edit and delete the app. Because the app lives in the same realm as our products, a person signed in to Tenantry is signed in to the customer's app too. Users of any other tenant cannot sign in to it.

The domain design comes from the project plan doc ("Customer applications", "Phase 4", "Security test suite") and ADR-0011. This spec records the choices those leave open. What does not work yet stays in `docs/known-issues.md`.

## Decisions taken for this phase

| Topic               | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| App types           | Four OIDC types: web app with a backend (`web`), single-page app (`spa`), mobile or desktop app (`native`), machine to machine (`m2m`). SAML apps move to a later phase (known issues, ADR-0011 update).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Who may use it      | Enterprise workspaces only (ADR-0011). `apps:read` (every role) lists apps and shows connection details; `apps:register` (owner, admin) registers, edits, rotates and deletes. A Standard workspace gets 404 "Applications are available on Enterprise workspaces", and the portal shows that sentence instead of the page.                                                                                                                                                                                                                                                                                                                                                                   |
| Record of an app    | Postgres is the record: a `tenant_apps` row with forced row-level security. The Keycloak client is written inside the row's transaction, so a Keycloak refusal rolls the row back; if Keycloak succeeded and the commit fails, the API deletes the client it made. Lists and details read Postgres only.                                                                                                                                                                                                                                                                                                                                                                                      |
| Secrets             | Never stored by us. Registering a `web` or `m2m` app and rotating its secret return the secret once in the response; the portal shows it in a notification and keeps it nowhere. Rotation invalidates the old secret at once.                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Keycloak access     | A new `RealmApps` interface in `packages/keycloak-admin` (HTTP implementation with the realm's `tenantry-backend` credential, in-memory fake in `/testing`). Client ids are generated as `app-<8 hex>`. Every customer client carries the attribute `tenantry.app=true`; `RealmApps` refuses to update, rotate or delete a client without it, so our four product clients can never be changed through it.                                                                                                                                                                                                                                                                                    |
| Customer app tokens | Customer clients get `fullScopeAllowed: false` and no role scope mappings, so their tokens carry neither the `tenantry-api` audience nor workspace roles. The guard's enterprise path also requires `azp` to be `tenantry-web` or `tenantry-portal`. A token issued to a customer app gets 401 on our API (new guarantee).                                                                                                                                                                                                                                                                                                                                                                    |
| Client per type     | `web`: confidential, authorization code only. `spa`: public, authorization code with PKCE S256, web origins from the redirect URIs unless given. `native`: public, PKCE S256. `m2m`: confidential, client credentials only, no browser flow. All: no implicit flow, no password grant, front-channel off, `post.logout.redirect.uris` from the form.                                                                                                                                                                                                                                                                                                                                          |
| URI rules           | One Zod schema in `packages/auth`, used by the API and the portal. Redirect and post-logout URIs: `https://` with a real host; `http://127.0.0.1[:port]` and `http://[::1][:port]` (loopback); for `native` only, a private-use scheme containing a dot (`com.acme.app:/callback`). Refused: `http` on any other host, `localhost` names ("use 127.0.0.1"), a `*` in the host, a fragment, more than 10 URIs per list. Web origins: scheme, host and port only.                                                                                                                                                                                                                               |
| Cap                 | 20 apps per workspace (`TENANTRY_MAX_APPS_PER_TENANT`, default 20). The 21st answers 409.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Realm template v2   | The secure-redirect-URI executor moves to a profile that applies to every client, with `allow-private-use-uri-scheme` and `allow-loopback-interface` on. Public clients keep PKCE. As in v1, a stack on `http` leaves that executor out (ADR-0010). `TEMPLATE_VERSION` becomes 2; existing realms move with `pnpm ops enterprise upgrade`, which the seed now runs.                                                                                                                                                                                                                                                                                                                           |
| Editing             | Name, redirect URIs, post-logout URIs and web origins can change; the type cannot (delete and register again). Keycloak first, then the row and the audit entry, in one transaction.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Deleting            | A dialog that needs the app's name typed. Deletes the Keycloak client (already gone counts as done), then the row.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| Test login          | `web`, `spa` and `native` clients also get the portal's `<portal origin>/applications/test-callback` as a redirect URI, shown as "Tenantry test sign-in" and not editable. The button runs authorization code with PKCE through a helper in `packages/oidc-client`. On return: `spa` and `native` exchange the code and show issuer, subject, audience and expiry; `web` (no secret to exchange with) shows that Keycloak signed in the person for this app; any error shows Keycloak's error and description. `m2m`: "Request a token" posts the pasted secret to the API, which asks Keycloak for one client-credentials token and reports the outcome; the secret is not logged or stored. |
| Connection details  | Issuer, discovery URL, authorization, token, JWKS and end-session endpoints, client id, scopes `openid profile email`, and the secret line ("shown once" for `web` and `m2m`, "none, public client" for `spa` and `native`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Setup snippets      | Three, filled with the app's real values: Node with `openid-client` (`web`, `m2m`), browser with `oidc-client-ts` (`spa`), `curl` client-credentials (`m2m`). `native` shows the connection details and the guide link. Each has a unit test.                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Audit               | `app.registered`, `app.updated`, `app.secret_rotated`, `app.deleted`, `app.token_checked`, with the app's name and client id; never a secret.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Example app         | `examples/customer-app`: an Express server with `openid-client`, a `web` app on `http://localhost:4000` (registered with `http://127.0.0.1:4000/callback`), configured from `ISSUER`, `CLIENT_ID`, `CLIENT_SECRET`. Home shows who is signed in; sign out ends the realm session. `pnpm example:customer-app` runs it.                                                                                                                                                                                                                                                                                                                                                                        |
| Seed                | Registers "Initech HR" (`web`, the example app's redirect) through the API when missing, and prints its client id. Its issuer, client id and secret are written to `examples/customer-app/.env` (git-ignored, written by the host, not a container) for the example app to read; the secret is never printed. A second seed run keeps the app and the file as they are.                                                                                                                                                                                                                                                                                                                       |

## Exit criteria

1. On `initech.portal.tenantry.localhost` the owner registers one app of each type, sees the secret once for `web` and `m2m`, and runs the test login or token check successfully.
2. With the seeded "Initech HR" app, `pnpm example:customer-app` signs in Initech's owner with no login page after they signed in to the portal; signing out of it ends the portal session too.
3. A redirect URI with a wildcard host, plain `http` on a non-loopback host, or a `localhost` name is refused by the API; a client written straight to the realm with a wildcard or `http` redirect is refused by Keycloak under template v2 over https.
4. Rotating a secret makes the old one fail; deleting an app removes its client.
5. The README rows for Phase 4 and the new "Token issued to a customer app is used on our API → 401" row are `tested`.
6. `pnpm lint typecheck test build`, `pnpm test:scripts`, `pnpm smoke`, `pnpm seed` twice (the second changes nothing) and `pnpm test:isolation` pass, locally and in CI.

Out of Phase 4: SAML apps, per-app consent and extra scopes, detecting clients edited in the Keycloak console, customer apps on Standard workspaces, app logos, rate limits on registration (Phase 6).

## Data model

`tenant_apps`: `id uuid pk`, `tenant_id` (RLS), `client_id text` (unique per tenant), `kc_client_uuid text`, `name text` (1–80 chars), `type text` check in (`web`, `spa`, `native`, `m2m`), `redirect_uris text[]`, `post_logout_redirect_uris text[]`, `web_origins text[]`, `created_by uuid` → `users`, `created_at`, `updated_at`. No secret column.

## API

All on the tenant's host; enterprise only.

| Method and path                  | Permission      | Does                                                     |
| -------------------------------- | --------------- | -------------------------------------------------------- |
| `GET /api/apps`                  | `apps:read`     | List, newest first                                       |
| `GET /api/apps/:id`              | `apps:read`     | One app with its connection details                      |
| `POST /api/apps`                 | `apps:register` | Register; 201 with `{ app, clientSecret? }`              |
| `PATCH /api/apps/:id`            | `apps:register` | Edit name and URI lists                                  |
| `POST /api/apps/:id/secret`      | `apps:register` | Rotate; `{ clientSecret }` (`web`, `m2m` only, else 409) |
| `POST /api/apps/:id/token-check` | `apps:register` | `m2m` only; body `{ clientSecret }`; `{ ok, error? }`    |
| `DELETE /api/apps/:id`           | `apps:register` | Delete; 204                                              |

Errors: 400 with field messages for invalid input (including Keycloak's refusal reason), 404 for an unknown or other tenant's id and for Standard workspaces, 409 for the cap, 502 when Keycloak is unreachable.

## Testing

- **Unit:** URI schema (each accept and refuse case above); snippets per type; per-type client representation; portal wizard steps and errors, secret shown once and gone after reload, delete confirmation, test-login result per type.
- **Keycloak contract** (fake and real Keycloak, same suite): create per type, refuse to touch a client without `tenantry.app`, rotation invalidates the old secret, delete of a missing client succeeds; template v2 over https refuses a wildcard and an `http` redirect.
- **API integration:** secret returned once and absent from the table; cap 409; member 403; Standard 404; another tenant's id 404; Keycloak refusal leaves no row; audit entries without secrets.
- **Isolation suite** (full stack): API and realm refuse a bad redirect; tenant A's admin cannot register or edit on tenant B's host; another tenant's user cannot sign in to Initech's app; a customer app's token gets 401 on our API; SSO between the portal and the running example app, and single logout back.
- **Browser walk:** register each type, copy the secret, test login, example app sign-in without a login page, rotate, delete; light and dark, 375 px.

## Risks

| Risk                                                                 | Mitigation                                                                                                    |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| A customer client's token is accepted by our API                     | No role scope on customer clients, and the guard requires our own `azp`; isolation test.                      |
| `manage-clients` lets the backend account change our product clients | `RealmApps` touches only clients marked `tenantry.app`; contract test.                                        |
| Keycloak and the table disagree after a crash between the two writes | Keycloak write inside the row's transaction, compensating delete on commit failure; drift detection deferred. |
| Template v2 breaks existing realms                                   | Dry run first; the upgrade path is exercised by the seed and CI.                                              |
