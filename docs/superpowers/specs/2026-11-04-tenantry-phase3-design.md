# Tenantry — Phase 3 design: Enterprise realm provisioning

Date: 2026-11-04 · Status: draft for review

## Purpose

Phase 3 adds the second tier. An Enterprise tenant gets its own Keycloak realm, `ent-<slug>`, built from a versioned template, with our two apps and our API as clients in it. The API treats both tiers the same after its guard: one `TenantContext`, the same pages, the same permissions. A token from any other realm is refused.

The domain design comes from the project plan doc ("Enterprise tenant provisioning", "Auth boundary", "Phase 3") and ADRs 0004 and 0010. This spec records the choices those leave open. What does not work yet stays in `docs/known-issues.md`.

## Decisions taken for this phase

| Topic                         | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Where provisioning runs       | An API endpoint does the work and writes the audit entries: `POST /api/platform/enterprise-tenants` on the base domain. Operators call it with `pnpm ops enterprise provision`. ADR-0010 stays: provisioning is a product feature.                                                                                                                                                                                                                                                                                          |
| Who may call it               | A platform-operator token: issued by the `platform` realm to the `tenantry-ops` client (client credentials), with audience `tenantry-api`. A new decorator `@OperatorOnly()` checks the issuer and `azp`. No human platform-admin role or page in this phase.                                                                                                                                                                                                                                                               |
| Provisioning credential       | A master-realm client `tenantry-provisioner` whose service account holds only `create-realm`. Keycloak gives it admin rights over the realms it creates and nothing else (checked on 26.8.1: it manages a realm it made and gets 403 on `platform`). The API holds it; locally `pnpm dev:stack` creates it with the bootstrap admin.                                                                                                                                                                                        |
| Per-realm credential          | Each realm gets a confidential `tenantry-backend` client with `manage-users`, `view-users` and `manage-clients` in that realm only. Its secret is generated by us and kept behind a `SecretStore` interface. Locally that is a git-ignored file per realm (`.secrets/ent-<slug>.json`); a cloud secrets manager can implement the interface in Phase 6. Never in Postgres. ADR-0023.                                                                                                                                        |
| Realm template                | `infra/keycloak/templates/enterprise-realm.v1.json`: token and session lifetimes, password and brute-force policy, `verifyEmail`, login theme `tenantry`, and client policies (PKCE required, no wildcard redirect URIs, no implicit flow). Product clients live in `infra/keycloak/templates/product-clients/`: `tenantry-web` and `tenantry-portal` (public, PKCE, the tenant's two origins), `tenantry-api` (bearer-only, client roles `owner`, `admin`, `member`, audience mapper on the two apps), `tenantry-backend`. |
| Provisioning steps            | The plan doc's nine steps, idempotent. A rerun resumes where a failed run stopped; the tenant stays `provisioning` until the smoke test passes. No step deletes a realm.                                                                                                                                                                                                                                                                                                                                                    |
| First admin                   | Created in the new realm with the `owner` client role and an execute-actions email (set password, verify email) through Mailpit.                                                                                                                                                                                                                                                                                                                                                                                            |
| Upgrades                      | `pnpm ops enterprise upgrade [--tenant <slug>] [--dry-run]` calls `POST /api/platform/enterprise-tenants/upgrade`. It compares only the keys the template sets with the live realm and its product clients, prints the differences, and applies them unless it is a dry run. Each realm's `template_version` is updated after a successful apply.                                                                                                                                                                           |
| Guard, Enterprise path        | The tenant row says the tier. Enterprise: the issuer must equal `<auth>/realms/ent-<slug>` exactly; roles come only from `resource_access.tenantry-api.roles`; there is no organization claim. Standard is unchanged.                                                                                                                                                                                                                                                                                                       |
| Members on Enterprise tenants | Full members page, through a tier-agnostic `MemberDirectory` (one per tenant): Standard wraps the organization calls; Enterprise uses the realm's users and the `tenantry-api` client roles, with that realm's `tenantry-backend` credential. Inviting creates the user with the role and sends an execute-actions email; the invite row is accepted on their first sign-in; revoking an invite deletes a user who never signed in.                                                                                         |
| Apps on Enterprise tenants    | `auth-config` returns the tenant's realm issuer and that realm's `tenantry-web` or `tenantry-portal`, with no organization scope. SSO and single logout work inside the realm. The workspace switcher lists only the current enterprise workspace: an enterprise account belongs to one realm (README tier table).                                                                                                                                                                                                          |
| Signup                        | Self-service signup still creates Standard tenants only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Fold-ins from known issues    | Identity refresh: email and name are updated on every sign-in, and a `users` row is created only for someone who is a member. The header's product-name link navigates within the app. A guarantee test that a company identity provider cannot bring an email outside its verified domain.                                                                                                                                                                                                                                 |

## Exit criteria

1. `pnpm ops enterprise provision --slug initech --name "Initech" --admin-email owner@initech.test` makes a working tenant in under a minute; a second run changes nothing.
2. The first admin follows the Mailpit email, sets a password, and signs in to `initech.tenantry.localhost` and `initech.portal.tenantry.localhost` with one sign-in. Members, Projects, Audit log and Branding work, and their login page is Tenantry-themed with Initech's brand.
3. The owner invites a member, who signs in with the role given.
4. A token from `platform`, from another `ent-*` realm, or for another audience is refused with 401 on Initech's host. The README rows for Phase 3 are `tested`.
5. `pnpm ops enterprise upgrade --dry-run` prints the differences after a template change, and the real run applies them and raises `template_version`.
6. `pnpm seed` also provisions Initech. `pnpm lint typecheck test build` and `pnpm test:isolation` pass, locally and in CI.

Out of Phase 3: customer apps (Phase 4), SCIM and per-tenant policy pages (Phase 5), Standard → Enterprise migration (Phase 5), a platform-admin UI, deleting an enterprise tenant.

## Code structure (additions)

```
infra/keycloak/templates/enterprise-realm.v1.json      realm settings and client policies
infra/keycloak/templates/product-clients/*.json        tenantry-web, tenantry-portal, tenantry-api, tenantry-backend
packages/keycloak-admin/src/realms/                    RealmProvisioner (create, apply template, clients, first admin),
                                                       template diff, RealmDirectory (users + client roles in one realm)
packages/keycloak-admin/src/secrets/                   SecretStore interface, file implementation
apps/api/src/modules/enterprise/                       provisioning saga, upgrade, OperatorOnly endpoints
apps/api/src/modules/members/                          MemberDirectory chosen by tier (Standard: organizations; Enterprise: realm)
apps/api/src/auth/                                     tier-aware role extraction; identity refresh; OperatorOnly
apps/ops/src/commands/enterprise.ts                    provision, upgrade (call the API with a tenantry-ops token)
```

## Data model

No new tables. `tenants.tier` (`standard` | `enterprise`) and `tenant_identity` (`realm`, `issuer`, `template_version`) exist since Phase 1. `platformRepository` stops filtering on `tier = 'standard'` and returns the tier. `kc_org_id` is null for enterprise tenants.

## API

| Endpoint                                                | Auth     | Does                                                                                                                                                  |
| ------------------------------------------------------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/platform/enterprise-tenants`                 | operator | `{ slug, name, adminEmail }` → runs the steps; 201 with the tenant, or 200 when it was already active; 409 when the slug belongs to a Standard tenant |
| `POST /api/platform/enterprise-tenants/upgrade`         | operator | `{ slug?, dryRun }` → per realm: the differences, and whether they were applied                                                                       |
| `GET /api/tenants/:slug/auth-config`                    | public   | Unchanged shape; Enterprise answers its own realm and client, `organization: null`                                                                    |
| Members, invites, projects, audit, branding, workspaces | as today | Work on both tiers                                                                                                                                    |

## Provisioning steps (idempotent)

1. Record intent: the `tenants` row (`enterprise`, `provisioning`) and an audit entry `tenant.provisioning`.
2. Create realm `ent-<slug>` with the provisioner credential (skip if it exists).
3. Apply the realm template (settings, client policies, theme).
4. Create or update the product clients from their templates, with the tenant's two origins.
5. Generate the backend secret on first run and store it in the `SecretStore`; set it on `tenantry-backend`.
6. Create the first admin with the `owner` role and send the execute-actions email (skip if the user exists).
7. Register the issuer: `tenant_identity` (realm, issuer, template version).
8. Smoke test: discovery document and JWKS answer; a client-credentials token for `tenantry-backend` is issued.
9. Mark the tenant `active` and audit `tenant.created`.

## Testing

| Layer                        | Adds                                                                                                                                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Unit                         | template diff; tier-aware role extraction; `OperatorOnly`; SecretStore file implementation; identity refresh                                                                                               |
| Contract (fake and Keycloak) | `RealmDirectory` behaves like the organization directory for members and roles; provisioner steps are idempotent                                                                                           |
| Integration (API, Postgres)  | provisioning saga resume after each failing step; operator-only refusal for user tokens; members on an enterprise tenant                                                                                   |
| Isolation (whole stack)      | token from `platform` on an enterprise host → 401; token from another `ent-*` realm → 401; wrong audience → 401; enterprise owner of A on B's host → 401/403; company IdP email outside its domain refused |

## Risks

| Risk                                                   | Mitigation                                                                                            |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| Client policies JSON differs between Keycloak versions | The plan's first task applies the template to a throwaway realm and pins the shape in a contract test |
| Template diffs are noisy (Keycloak adds defaults)      | Compare only keys the template sets                                                                   |
| The API holds a realm-creating credential              | `create-realm` only; every use is audited; operator-only endpoint                                     |
| Realm count slows Keycloak                             | Measured in Phase 6                                                                                   |
